Stop re-sending what your session no longer needs.

tokenbrake has Claude Code compact at 300k tokens instead of near a million, hands the model its working set back after each compaction, and trims oversized tool output before it enters context. One install, every project.

npx tokenbrake init

Node 18+, no dependencies. npx tokenbrake uninstall takes it back out, the compaction window included when init set it.

8automatic compactions on the author's real work, Opus 5 and 5.5, over ten days
47.2 ptsof the five-hour window they saved; a point is 1% of that window
≤ 13.7 ptscame back: 0.9 in re-reads, up to 12.8 in compaction's own charge

Pre-registered, on one person's work. The limits are below, and the whole record is in EVIDENCE.md.

Size is the wrong number. Carried is the right one.

A tool result isn't paid for once. Every later request re-sends it as context until the session compacts, so a 4k-token file read at request 3 of 100 is about 400k token-reads. Most of that comes back from cache, and one cache read weighs little. But on a 1M-context model Claude Code compacts on its own only near 967k tokens, so a long session re-reads a growing context on every request, for hundreds of requests.

Compacting earlier cuts that short. The risk is the model losing its place and reading everything again, which is why the window and the working set ship together: each was measured only with the other.

What init installs

  1. A 300k compaction window. Claude Code's own setting, autoCompactWindow, in ~/.claude/settings.json. Nothing of tokenbrake's runs inside the compaction, and /autocompact changes it any time. init leaves a window you set yourself alone.
  2. The working set, put back. After each compaction a SessionStart hook hands the model pointers, never file contents: the files edited and read with their line ranges, the last failing command and its first error line, and the task's first words. About 2,000 tokens at most, so the model re-reads what its next step needs instead of searching for its place.
  3. A trim on oversized shell output. Output over 6,000 characters becomes its first and last lines, plus up to 20 lines from the middle that look like errors or warnings, with their line numbers. The full output is saved under ~/.claude/tokenbrake/out/ and the trimmed result names the path, so Claude can read it back.
  4. A cap on large reads. A Read with no range on a file over 60 KB becomes its first 300 lines, and Claude is told the file's real size and how to page through it.

Any error inside the hooks exits with no output, and Claude Code carries on unchanged. The ledger of result sizes stays on your machine. The rest of what tokenbrake can do to context, the MCP, JSON, git diff and re-read knobs, ships off until it is measured.

npx tokenbrake init      # user scope: ~/.claude/settings.json, every project
npx tokenbrake status    # what is installed, plus one real spawn of each hook
npx tokenbrake uninstall

As a Claude Code plugin it installs the hooks but writes no settings: set /autocompact 300k and compactPrep: true in ~/.claude/tokenbrake.json yourself. In cloud sessions it runs from the environment's setup script. See the install section.

What was measured, and what wasn't

The window and the working set passed two stages, each written down before its numbers were read.

  • Stage A, controlled, Opus 5. The same task with and without the working set: a median 4.18 points of the five-hour window against 5.49, and every recall question still answered, 15 of 15.
  • Stage B, the author's real work, 2026-09-20 to 09-29. 8 automatic compactions saved 47.2 points. Re-reading afterwards took back 0.9, and compaction's own charge 4.0 at its estimate, 12.8 at the pessimistic bound. The stage allowed up to half to come back; at worst 13.7 did. The work never felt worse.

The limits: one person's work, on Opus models with a 1M context. The recovery is inferred, and the saving assumes the same requests would have run without the earlier compaction. Headless claude -p compacts at 300k too, and that was not measured.

The trim is the smaller lever, and its record is thinner. In a pre-registered 22-session benchmark, pairs with the tool off on both sides came out up to 42.6% apart on tokens entered. Runs with the trim entered a median 35.7% fewer tool-result tokens, inside that noise, and tokens carried rose in two of six pairs, once by 72.6%, because a trim that sends the model back for what it cut makes the session longer. On the author's machine, 100 sessions to 2026-09-30 put the brake's net at about 55.6 points: 52.6 from the compactions, 3.0 from the trim.

The gauge: npx tokenbrake report

No install needed. report reads the transcripts Claude Code already keeps under ~/.claude/projects/ and ranks every tool result by size × the requests it was carried through. When the brake ran, it shows what it lowered, less what the model pulled back, against the whole session. --compactions prices every compaction; --detail is everything else.

Send your numbers

Everything above was measured on one machine. The next measurement needs other people's. After a few days with the brake installed, run:

npx tokenbrake report --share

It pools every session on your machine into one block of numbers: versions, the compaction window, tokens processed, the five-hour window by kind, the compactions, what the trim kept out and what came back, and the brake's net. No path, command, file name, session id or line of a transcript. Paste it into an issue, losses included.
