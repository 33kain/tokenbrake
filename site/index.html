tokenbrake

Find out what ate your Claude Code context.

Then brake it — if your report says there is anything to brake.

npx tokenbrake report

No install, no hooks, no config, nothing written anywhere. Node 18+.

Size is the wrong number. Carried is the right one.

A tool result isn't paid for once. It is re-sent as context on every later request until the session compacts, so a 4k-token file read at request 3 of 100 is about 400k token-reads. report reads the session transcripts Claude Code already keeps under ~/.claude/projects/ and ranks every tool result by size × the requests it was carried through. That puts the cat, Read or test run worth avoiding at the top, where you can see it.

This is the report from a real session spent building tokenbrake:

$ npx tokenbrake report
  487 requests, 443 tool results
  Context processed: 204.7M tokens across 487 requests (99% read from cache)
  Tool results entered ~ 140k tokens, carried ~ 41.2M token-reads

The last line matters most. The report tells you how much of what you carried a brake could reach at all. When tokenbrake wasn't running, it also tells you whether installing it is worth it for work like yours. Often it isn't, and the report says so.

Two steps, in this order

Step one · the report

npx tokenbrake report ranks the last session. --all lists every session on disk; --reach shows what share of your carried tokens any trim could act on.

Step two · the brake

npx tokenbrake init installs two Claude Code hooks. They trim oversized shell output and cap unbounded reads of large files before either enters context.

What the brake does

  • Shell output trim. Output over 6,000 characters is replaced by its first and last lines, plus up to 20 lines from the middle that look like errors or warnings, with their line numbers. The full output is saved to ~/.claude/tokenbrake/out/, and the trimmed result names that path so Claude can read it again. Nothing is rewritten or "compressed".
  • Large-read cap. A Read with no range on a file over 60 KB becomes the first 300 lines. Claude is told the file's real size and how to page through it.
  • Ledger. The size of every tool result is appended to a local file. Nothing leaves your machine.
  • Fails open. Any error inside the guard exits cleanly with no output, and Claude Code carries on unchanged.
npx tokenbrake init      # user scope: ~/.claude/settings.json, every project
npx tokenbrake status    # what is installed, plus one real spawn of each hook
npx tokenbrake uninstall

It also installs as a Claude Code plugin, and it runs in cloud sessions from the environment's setup script. See the install section.

Why there is no percentage on this page

A token-saving percentage in this category means nothing without a control pair: the same task run twice with the tool off on both sides. Without one, a saving can't be told apart from the agent simply reading differently that day.

tokenbrake ran those controls in a pre-registered 22-session benchmark. Pairs with identical configuration, tool off on both sides, came out up to 42.6% apart on tokens entered. Runs with the brake entered a median 35.7% fewer tool-result tokens, which is inside that noise. Tokens carried fell in only four of six pairs and rose in two, once by 72.6%, because a trim that sends the model back for what it cut makes the session longer.

So tokenbrake doesn't quote a saving. It reports what your own sessions carried and how much of that the brake could reach, and leaves the decision to you. The whole record, losses included, is in EVIDENCE.md.
